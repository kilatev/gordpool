# Выбор периодов без доступа к оборудованию

Основа: `master`, commit `e73874f09f8fcbbf7d544ff80e8a0344d2a67a5e`.

## Реализовано

- `optimize_periods(prices, battery, now)` — чистая функция, без сети, браузера, чтения секретов или настроек устройства.
- Горизонт — следующие 24 реальных часа, только опубликованные цены. Текущий и последний интервалы обрезаются по оставшейся длительности. Отсутствующие цены не дополняются прогнозом.
- Динамическое программирование выбирает последовательность SOC на сетке 1%. В состояние входят заряд, использованный лимит циклов, число открытых окон и предыдущее действие. Ограничения учитываются при поиске, а не удалением лишних окон из готового плана.
- Не более двух непрерывных окон заряда и двух использования энергии. HOLD закрывает окно. Полночь не разрывает непрерывный период; результат содержит абсолютные timestamps, а не ежедневные настройки инвертора.
- Заряд из сети ограничен 6 кВт, включая потери. Дополнительно действует заданный пользователем предел мощности на стороне батареи. Сохранены КПД, износ, лимит циклов, границы и начальный SOC.
- Линейная стоимость перехода SOC позволяет вычислять скользящий минимум через deque вместо перебора всех пар начального и конечного SOC. Хранятся только достижимые состояния и обратные ссылки для восстановления плана.
- При денежных различиях менее `1e-12 EUR` предпочтение отдаётся меньшему движению энергии и меньшему числу активных интервалов, чтобы ошибка float не создавала лишние циклы.
- Новая функция доступна через `POST /v1/plan/periods`, CLI `--periods` и выбранный по умолчанию режим UI. Прежний `/v1/plan` и прежняя функция `optimize()` доступны для сравнения.

## Проверка

`tests/test_periods.py` содержит проверки свойств в духе QuickCheck средствами unittest и генератора random с фиксированным seed. Это не Hypothesis: автоматического уменьшения контрпримеров нет; при ошибке subTest выводит сгенерированные входные данные.

- 100 сгенерированных маленьких задач сравниваются с независимым полным перебором всех SOC-траекторий. Оракул отдельно проверяет мощность, число окон, цикл-бюджет и вычисляет целевую функцию. Варианты включают отрицательные цены, потери, износ, запрет действий, разный начальный SOC и стоимость остатка.
- Ещё 80 сгенерированных сценариев проверяют сохранение энергии, связность SOC, границы заряда, ограничения окон и мощности, согласованность периодов со слотами и сводкой. Ослабление ограничения с одного окна до двух не должно ухудшать результат; старый неограниченный алгоритм даёт верхнюю границу результата.
- Регрессии: заряд 8 кВт·ч не помещается в один четвертьчасовой слот; выгодные два использования выбираются из трёх пиков; равные цены не создают циклов; изменение переданного SOC меняет нужный заряд; цены за пределами 24 часов не влияют на результат или медиану; частичные интервалы, полночь и DST.
- `tests/test_periods_api.py`: синтетический Nord Pool HTTP → настоящий парсер → JSON-снимок → новый экземпляр API → план периодов. Отдельно проверены пересчёт по новому SOC и отклонение неверного SOC без доступа к устройству.

Локально: 44 теста прошли, 4 пропущены (три браузерных без Playwright в используемом venv и opt-in live-тест). `optimizer.py`: 100% строк и ветвей; новый `periods.py`: около 98% с учётом ветвей. Это не проверка реального оборудования. Локальный offline replay и проверка синтаксиса JS также прошли.

На одном синтетическом суточном сценарии замена перебора переходов скользящим минимумом сократила время нового планировщика примерно с 0.47 до 0.11 с без лимита циклов. С лимитом одного эквивалентного цикла расчёт занял около 7 с; исходный вариант не завершился за 15 с. Это одиночные измерения в одной среде, не стабильный benchmark и не SLA.

## Что намеренно не подключено

Модули `solax_charge.py`, `solax_soc.py`, `solax_control.py` и `scheduler.py` не изменены и не запускались для доступа к устройству. Существующая облачная автоматизация продолжает использовать прежний алгоритм и адаптер; новый расчёт к ней автоматически не подключается.

Не реализованы чтение целевого/минимального SOC из SolaX, запись двух периодов, включение периода 2 и проверка сохранения, ежедневное повторение расписания устройства или событийный scheduler. Это отдельный этап после проверки алгоритма и явного подключения к оборудованию.

Уровни SOC задаются вручную или передаются вызывающим кодом. Верхняя граница SOC не означает обязательный заряд до неё; выбираются выгодные возможности. Жёсткий конечный резерв не добавлен. Стоимость остатка по умолчанию — медианная цена рассматриваемого горизонта; для анализа завершённых циклов задать 0. Реальные нагрузка дома и PV не известны: `executable` остаётся false, а разряд оценивается как потенциальное замещение покупок при достаточной нагрузке, не как экспорт или подтверждённая экономия.

## Команды

Из каталога `python/`:

```bash
python -m unittest tests.test_periods tests.test_periods_api -v
python -m solax_optimizer examples/request.json --periods
curl -H 'Content-Type: application/json' --data-binary @examples/request.json http://127.0.0.1:8000/v1/plan/periods
```

Все перечисленные тесты и offline replay используют синтетические входы. Они не запускают scheduler, браузер SolaX или Cloud API.
