# SolaX Price Planner — Python MVP

## Планирование нескольких периодов без устройства

Новый режим отчёта: **24 часа · до двух окон каждого типа**. Он выбирает периоды непосредственно в динамической модели, с учётом нужной энергии, SOC, КПД, износа и лимита заряда **6 кВт из сети**. Прежний расчёт всего горизонта остаётся доступен в переключателе режима.

API: `POST /v1/plan/periods`. Offline replay: `python -m solax_optimizer examples/request.json --periods`. Входы те же, что у `/v1/plan`; начальный и предельные SOC задаются пользователем. Результат дополнен `planning_constraints`.

Это отдельный расчёт без обращения к SolaX. Облачный адаптер и scheduler не изменены и автоматически новый алгоритм не применяют. Ограничения модели и подробности 180 сгенерированных сценариев и интеграционных проверок — в [PERIOD_PLANNING.md](PERIOD_PLANNING.md).

Ценовой планировщик Nord Pool LV: Python, FastAPI, Rocketry. API и планировщик ничего не записывают в SolaX. Отдельная ручная CLI-команда `solax_charge` ниже меняет период заряда через браузер.

Перенос динамического программирования из `kilatev/gordpool/pkg/planner/optimize.go`, исходный commit `97252f4015b02526d44a563093898a59a7b4acd4`. Сетка SOC 1%, планирование всего опубликованного горизонта, КПД, износ, пределы мощности, необязательный лимит циклов. Модель использует **виртуальную** батарею с настраиваемыми параметрами, а не телеметрию реальной батареи.

## Запуск на Linux

```bash
uv sync --extra test
uv run uvicorn solax_optimizer.api:app --host 127.0.0.1 --port 8000 --workers 1
```

В другом терминале, из того же каталога:

```bash
uv run python -m solax_optimizer.scheduler
```

Rocketry работает отдельно от веб-сервера. Сначала обновляет цены при старте, затем проверяет источник каждые 15 минут в 12:00–18:00 Europe/Riga и один раз в первые 15 минут после полуночи. Это окно опроса, не утверждение о гарантированном времени публикации. `flock` запрещает второй планировщик в том же каталоге. При сетевой ошибке остаётся предыдущий JSON-снимок; ошибки попадают в журнал. После перезапуска снимок читается с диска, очередной запуск пересчитывает даты. Несколько независимых каталогов/серверов этой блокировкой не защищены.

Версии ограничены совместимостью Rocketry 2.5.1 с Pydantic 1.10; использовать отдельное окружение. FastAPI ограничен веткой до 0.120. `uv.lock` фиксирует разрешённые версии. Не устанавливать эти зависимости в существующее приложение с Pydantic 2.

## API

- `GET /` — интерфейс отчёта: график цен и действий, периоды с объяснениями и детализацией по интервалам, настройки виртуальной батареи, отдельная оценка остатка и скачивание JSON. Время Europe/Riga со смещением UTC; это позволяет различать повторный час DST.

- `GET /healthz` — работоспособность API, не свежесть цен.
- `POST /v1/prices/refresh` — получить сегодня/завтра; без изменения настроек оборудования.
- `GET /v1/prices` — снимок, время загрузки и предупреждения.
- `POST /v1/plan` — план по снимку либо собственным `prices`, `battery`, `now`.
- `/docs` — интерактивная схема API.

Локальное воспроизведение без сети:

```bash
uv run python -m solax_optimizer examples/request.json
curl -H 'Content-Type: application/json' --data-binary @examples/request.json http://127.0.0.1:8000/v1/plan
```

Пример синтетический, не исторические цены. `now` и все интервалы содержат часовой пояс. API возвращает UTC; для отображения перевести в Europe/Riga, сохраняя смещение при повторном часе DST.

Цены передаются в EUR/MWh, затраты — в EUR, энергия — в кВт·ч. Мощность и износ — на стороне батареи. КПД заряда и разряда равны квадратному корню полного КПД, как в Go. Для ограничения **сетевой** мощности потребуется отдельная модель. Нулевой предел мощности означает отключение соответствующего движения.

`CHARGE`, `HOLD`, `DISCHARGE` — логические ценовые возможности. `potential_use_kwh` оценивает использование дома при наличии достаточной нагрузки; это **не команда экспорта**. Фактическое потребление дома, солнечная генерация, фазные ограничения, тарифные надбавки и реальные настройки инвертора в этом MVP ещё не моделируются. `executable` всегда false.

`potential_cash_benefit_eur` — условная стоимость замещённых покупок минус заряд и износ. `terminal_value_change_eur` — отдельная оценка изменения остатка; это не деньги на счёте. Сумма даёт `objective_benefit_eur`, по которому выбирается план. Если `stored_energy_value_eur_kwh` отсутствует, как в Go используется медианная цена горизонта; это может создавать заряд ради конечного остатка. Для анализа завершённых циклов указать 0 и начальный SOC на минимуме. Жёсткий конечный резерв пока не реализован.

## Обработка цен

Источник из Go: `https://dataportal-api.nordpoolgroup.com/api/DayAheadPrices`, параметры `market=DayAhead`, `deliveryArea=LV`, `currency=EUR`.

Сохраняем явные начало и конец, проверяем 15 минут, конечные числа, дубликаты, разрывы и полноту торгового дня. Границы `deliveryDateCET` считаются в Europe/Stockholm (CET/CEST), а время опроса — в Europe/Riga. Сутки с переходом времени содержат 92 или 100 интервалов. Контракт источника проверен синтетическими ответами; живое получение цен LV подтверждено 28 октября 2026.

Пустой `multiAreaEntries` означает отсутствие опубликованных цен. Ошибка/неполнота завтра не уничтожает валидные сегодняшние цены, но отражается в предупреждениях. Прошедшие интервалы не исполняются; начавшийся интервал учитывается только оставшейся длительностью. Пустой будущий горизонт отклоняется.

## Тесты

```bash
uv run --extra test python -m unittest discover -v
uv run --extra test pytest --cov=solax_optimizer --cov-branch --cov-report=term-missing
```

В тестах: численный сценарий из Go, ожидание абсолютного минимума и максимума, несколько циклов, мощность, потери/износ, отрицательные цены, лимит циклов, частичный интервал, ошибки входов, энергетические инварианты на случайных кривых и независимый полный перебор маленьких задач. Также проверяются источник через HTTP MockTransport, DST, отсутствие завтра, FastAPI, атомарная запись, сохранение снимка при ошибке и временные окна планировщика.

На целевых FastAPI 0.119.1 / Pydantic 1.10.26 / Rocketry 2.5.1 локально прошли 27 тестов, покрытие Python-кода с учётом ветвей — 91%. Регистрация Rocketry проверена; работа планировщика по реальным часам пока не проверена. Подробности и команды — в `TESTING.md`.

## Отчёт без SolaX Cloud

Открыть `http://127.0.0.1:8000/` после запуска API. «Обновить Nord Pool» получает опубликованные цены LV. «Открыть демо» строит план по явно помеченным синтетическим ценам без сети. Параметры батареи можно менять и пересчитывать; раскрытие периода показывает цену и мощность каждого интервала. Смежные действия объединяются в период, но мощность внутри может меняться. Объяснения описывают модель оптимизации, а не доказывают причинность каждого отдельного действия.

Демо не сохраняет цены на диск и не меняет снимок Nord Pool. При ошибке обновления предыдущий отчёт остаётся виден с сообщением, что новые параметры ещё не применены. Кнопка скачивания экспортирует именно показанный расчёт, снимок и параметры.

Playwright запускает настоящий Chromium и локальный Uvicorn; аккаунт SolaX и доступ к Nord Pool ему не нужны:

```bash
uv sync --extra test --extra browser
uv run python -m playwright install chromium
uv run python -m unittest tests.browser.test_report -v
```

Для системного Chromium можно задать `GORDPOOL_CHROMIUM_PATH=/usr/bin/chromium`. В CI браузерные проверки вынесены в отдельное задание, скриншоты сохраняются в артефакте `browser-report`. Локальный запуск Chromium ограничен сетевой песочницей; успешный результат этих трёх тестов пока не заявляется.

До управления оборудованием нужны модель нагрузки без экспорта, конечный резерв, ограничения переключений и подтверждение семантики реального UI.

## Ручная установка периода заряда через Playwright

Из каталога `python`, после `uv sync --extra browser`:

```bash
uv run python -m solax_optimizer.solax_charge --serial H34A15J7S18051 --start 04:00 --end 05:00
# Обнулить оба поля:
uv run python -m solax_optimizer.solax_charge --serial H34A15J7S18051 --start 00:00 --end 00:00
# Взять данные входа из Proton Pass, если Chromium открыт на странице входа:
uv run python -m solax_optimizer.solax_charge --login --serial H34A15J7S18051 --start 04:00 --end 05:00
```

С `--login` CLI читает поля `email` и `password` из Proton Pass (`pass-cli`, хранилище `cli`, запись `solaxcloud.com `). При необходимости укажи другие `--pass-vault`, `--pass-item` и `--pass-login-field`. Скрипт заполняет форму, отмечает единственный видимый checkbox согласия и нажимает Login. Используй это только если согласен с условиями SolaX; если форма неоднозначна или её элементы не распознаны, скрипт остановится.

Нужен авторизованный Chromium с доступным CDP (по умолчанию
`http://127.0.0.1:9222`, другой адрес — `--cdp-url`). Подключение расширения
Codex само по себе не предоставляет этот порт Python-скрипту. Для профиля с CDP
запусти браузер вручную:

```bash
chromium --remote-debugging-address=127.0.0.1 --remote-debugging-port=9222 \
  --user-data-dir="$HOME/.local/share/solax-automation"
```

Без `--login` заранее войди в SolaX и оставь страницу Overview открытой. С `--login`
можно оставить страницу входа: скрипт возьмёт логин и пароль из Proton Pass,
отметит согласие с условиями и нажмёт Login.
Затем скрипт сам пройдёт Overview → Devices → Manage выбранного по серийному номеру
инвертора → Remote Settings → Settings → User Settings. При запросе пароля настроек
он введёт `0000`; другое значение можно передать через `--settings-password`.
Если Remote Settings не загрузится,
он завершится до изменения периода. CDP даёт управление всем профилем браузера:
держи порт локальным и не используй в этом профиле посторонние сайты.

Команда проверяет серийный номер на странице, выбирает часы и минуты, нажимает
Confirm и Save отдельно для каждого поля. После каждой записи перезагружает
страницу и проверяет сохранённое значение; браузер остаётся открытым.
Период разряда и Function не меняются. Время — в системе отсчёта UI инвертора,
без конвертации часового пояса. `00:00–00:00` только обнуляет эти поля;
скрипт не проверяет другие причины заряда и не подтверждает физическое состояние батареи.

Записи нескольких полей не атомарны: при ошибке часть расписания могла уже сохраниться.
Команда останавливается с ненулевым кодом, без автоматического отката или повторов;
проверить поля в браузере. API управление оборудованием не запускает; scheduler
делает это только при явном `SOLAX_CONTROL_ENABLED=1`.

## Автоматическое применение плана

При запуске через `just run` планировщик после обновления цен запускает `optimize()` и записывает в SolaX по одному непрерывному окну заряда и разряда: самое дешёвое окно заряда и самое дорогое окно разряда среди выбранных оптимизатором. Используется инвертор `H34A15J7S18051`; войди в SolaX в открытом Chromium, чтобы управление сработало.

Планировщик сохраняет цены и обновляет расписание после успешного обновления цен
каждые 15 минут в окне публикации, а также при старте. Chromium с активной SolaX-сессией
должен оставаться запущенным. `SOLAX_CDP_URL` задаёт адрес CDP, `SOLAX_TIMEZONE` —
часовой пояс расписания (по умолчанию `Europe/Riga`). Если оптимизатор не выбрал
окно заряда или разряда, соответствующий период устанавливается в `00:00–00:00`.
Перед каждым расчётом автоматизация читает SOC инвертора с Overview и передаёт его
как начальный SOC оптимизатору. Если значение для выбранного инвертора нельзя прочитать
однозначно, пересчёт и запись расписания завершаются ошибкой.

Только прочитать SOC вручную:

```bash
cd python && uv run python -m solax_optimizer.solax_soc --serial H34A15J7S18051
```

Расчёт использует текущие значения `Battery()` из оптимизатора (в частности,
ёмкость 10 кВт·ч и мощность заряда и разряда 5 кВт). Это модель ценового арбитража:
она не учитывает тепловую нагрузку или комфортную температуру и не управляет тепловыми
насосами. Поэтому расписание отражает текущий планировщик, а не измеренную экономию
отопления.

Проверка без аккаунта и оборудования:

```bash
uv run python -m unittest tests.test_solax_charge -v
```

Скрипт запускался на авторизованном инверторе: прошёл путь от Overview, сохранил оба
поля и подтвердил значения после перезагрузки. CDP используется согласно
[документации Playwright](https://playwright.dev/python/docs/api/class-browsertype#browser-type-connect-over-cdp).
